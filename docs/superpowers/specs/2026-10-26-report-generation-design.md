# 报告生成能力设计

**日期**：2026-10-26
**状态**：已评审，待实现
**关联**：`skills/report-writer/`、`scripts/collect.py`、`scripts/render.py`

## 1. 背景与目标

工具包目前有三个能力：批量造数、数据库访问、接入新业务。它们解决的是「造数据和查数据」。

本次增加第四个能力：写日报、周报、月报、述职报告。目标是把日常散落在 git 提交和禅道任务里的工作记录，
整理成可直接提交的汇报材料，减少每次从头回忆和排版的时间。

成功标准：

- 说一句「写今天的日报」，能在 1 分钟内产出一份内容准确的稿子
- 报告里的数字（提交数、任务数）与实际记录一致，可复现
- 同一句需求可以按需要同时产出 Markdown、Word、PPT

## 2. 范围

**做**

- 四种报告：日报、周报、月报、述职
- 两种数据源：git 提交、禅道任务与 Bug
- 三种输出：Markdown、Word、PPT
- 生成前询问受众，按受众调整语气
- 项目级模板（文本结构模板）

**不做**

- 定时自动生成（由用户触发）
- 推送到飞书 / 邮件 / 企业微信
- 禅道 API v1（当前环境只有 v2，等有环境再补）
- 填写二进制 Word 模板（只支持文本结构模板）
- 团队多人报告汇总

## 3. 总体架构

新增第四个技能 `report-writer`，与现有三个并列。数据流分三段：

```
collect.py ──> JSON（确定性、可复现、可测试）
                    │
             技能读 JSON + 询问补充
                    │
                Markdown（内容层，唯一真相来源）
                    │
              render.py ──> .docx / .pptx
```

**拆分原则**：采集和渲染是确定性代码，可单测；AI 只负责中间「把结构化事实和用户口述组织成文字」。
这样日期、作者、条数不会每次跑出不同结果，Word/PPT 排版也不会因模型发挥而变样。

新增文件：

| 路径 | 职责 |
|---|---|
| `skills/report-writer/SKILL.md` | 触发条件、范围判定、受众询问、组织规则 |
| `scripts/collect.py` | 采集 git 与禅道，输出 JSON |
| `scripts/render.py` | Markdown → docx / pptx |
| `tests/test_collect_git.py` | 提交筛选与时间区间 |
| `tests/test_collect_zentao.py` | 禅道驱动与分页 |
| `tests/test_render.py` | 三种格式渲染 |

新增依赖：`python-docx`、`python-pptx`。

## 4. 数据源与范围定位

### 4.1 项目定位

按顺序，命中即停：

1. 用户明确指定项目 → 用它
2. 当前工作目录落在某项目配置的仓库路径下 → 用该项目
3. 对不上，或同时命中多个 → 询问，不猜

### 4.2 项目配置

位置：`~/.data-tools/projects/<项目ID>/report.yaml`

```yaml
git:
  repos:
    - C:/project/hexincloud
    - C:/project/claudeTool
  authors:
    - 1739498098@qq.com

zentao:
  api: auto                 # auto | v1 | v2
  base_url: ${ZENTAO_URL}
  account: ${ZENTAO_ACCOUNT}
  product_id: 31
  project_ids: [73]

period:
  week_starts_on: monday
```

凭据写在同目录 `.env`，与适配层共用一份，不新增凭据文件。

### 4.3 git 采集

- 对每个仓库执行只读 `git log`，按作者和日期区间筛选，跳过合并提交
- 取字段：短 hash、日期、标题、改动文件数、分支
- 作者支持多个，覆盖不同机器不同邮箱
- 仓库路径不存在或不是 git 仓库时跳过并记录

### 4.4 禅道采集

自建薄客户端，不依赖 `dev-overlay` 的脚本，但复用同一个 token 缓存 `~/.zentao-token.json`。

认证：`POST {base_url}/api.php/v2/users/login`，body 为 `account` + `password`，响应取 `token`；
后续请求 Header 携带 `token`。token 过期时重新登录一次，仍失败则记录失败原因。

端点：

| 数据 | 端点 | 参数 |
|---|---|---|
| 执行列表 | `/projects/{id}/executions` | 分页 |
| 任务 | `/executions/{id}/tasks` | `browseType=assignedtome`、`recPerPage`、`pageID` |
| Bug | `/products/{id}/bugs` | `browseType=assignedtome` |

任务不跨执行直查，需要先枚举执行再逐个拉取；同一次采集中缓存已拉取的结果。

`api: auto` 时先探测 v2 登录端点，失败再尝试 v1；本期只实现 v2，`v1` 分支返回明确的「未实现」错误。
两个驱动都必须输出同一结构。

### 4.5 中间产物

```json
{
  "project": "hexincloud",
  "period": { "type": "weekly", "start": "2026-10-19", "end": "2026-10-25" },
  "sources": { "git": "ok", "zentao": "failed: 401" },
  "git": [
    { "repo": "hexincloud", "commits": [
      { "hash": "a1b2c3d", "date": "2026-10-21", "subject": "feat: ...", "files": 3 }
    ]}
  ],
  "zentao": { "tasks": [], "bugs": [] }
}
```

`sources` 记录每个源的状态。任何源失败都必须在报告开头体现，不允许静默缺失。

## 5. 报告类型与结构

四种类型各自独立生成，周报不汇总日报，月报不汇总周报，全部从原始数据生成。

| 类型 | 时间范围 | 默认结构 |
|---|---|---|
| 日报 | 当天 | 今日完成 / 明日计划 / 风险与需要支持 |
| 周报 | 周一至周日 | 本周完成 / 关键数据 / 问题与风险 / 下周计划 |
| 月报 | 自然月 | 目标达成 / 关键成果 / 问题与改进 / 下月重点 |
| 述职 | 用户指定 | 成果 / 问题与反思 / 规划；提供模板时按模板 |

### 5.1 组织规则

1. 写结果，不写动作。不出现「提交 12 次代码」，改为「完成提货单状态流转，覆盖 5 个环节」
2. 合并去重。同一件事既有提交又有任务时合并成一条，以任务标题为主线
3. 数字只作佐证，不堆砌。日报 200–400 字，周报 400–800 字，月报 800–1500 字

### 5.2 受众与语气

生成前询问受众，默认沿用上次选择。上次选择记录在本机
`~/.data-tools/reports/<项目ID>/.audience`，每个项目独立记忆：

| 受众 | 语气 |
|---|---|
| 直属领导 | 简洁、结果导向、少形容词（默认） |
| 更高层 | 更聚焦业务价值与风险，细节下沉 |
| 自己留痕 | 可以写过程、待办和踩坑 |
| 团队共享 | 强调协作接口与依赖关系 |

### 5.3 口述补充

采集完成后先摆事实（提交数、任务数、Bug 数），再询问「有什么没体现在提交和工单里的」。
用户补充内容优先级最高，直接进入对应章节。

## 6. 模板

位置：`~/.data-tools/templates/<项目ID>/<类型>.md`

模板只定义章节标题与提示语，不参与内容逻辑：

```markdown
## 本周完成
<!-- 写结果，不写过程；按业务主题分组 -->

## 数据支撑
<!-- 提交数、完成任务数、修复 bug 数 -->
```

没有模板时使用内置默认结构。模板缺失或解析失败时回退到默认结构并提示。

## 7. 输出格式与命名

输出格式由用户多选：Markdown、Word、PPT。Markdown 是唯一真相来源，Word 与 PPT 均从它渲染，
修改内容只需改 Markdown 后重新渲染。

- Word：A4，统一标题层级，`python-docx`
- PPT：标题页 + 每个二级标题一页，每页最多 6 条要点，超长自动续页，白底单主色

存放位置与命名：

```
~/.data-tools/reports/<项目ID>/
├── 2026-10-26-daily.md
├── 2026-W43-weekly.md
├── 2026-10-monthly.md
└── 2026-Q3-review.pptx
```

同一周期重跑直接覆盖。周报使用 ISO 周编号（`2026-W43`），季度使用 `2026-Q3`。

## 8. 失败处理

| 情况 | 行为 |
|---|---|
| 仓库路径不存在或不是 git 仓库 | 跳过并记录，其它仓库照常 |
| 禅道连不上 / 登录失败 / 分页中断 | 记录原因，继续出报告 |
| 任一数据源缺失 | 报告开头写明缺失范围 |
| 完全无数据 | 不编造，输出骨架并说明无记录 |
| 项目无法确定 | 停止并询问 |
| 时间区间非法 | 报错，不生成 |
| 渲染依赖缺失 | Markdown 照常产出，提示安装 |

核心原则：不把「跑完了」当「跑对了」，数据缺失必须显式说明。

## 9. 隐私与安全

- 报告含工作内容，只存 `~/.data-tools/reports/`，不进 git
- 凭据只来自项目 `.env` 与 `~/.zentao-token.json`，不写入报告
- 采集为只读操作，不修改任何仓库或禅道数据

## 10. 测试策略

- `test_collect_git`：临时 git 仓库，多作者多日期提交，验证筛选
- `test_collect_period`：日/周/月/季度的时间边界
- `test_collect_zentao`：本地假 HTTP 服务返回 v2 报文，验证分页与字段归一化
- `test_collect_partial`：禅道失败时 `sources` 标记失败且 git 数据完整
- `test_render`：临时目录渲染三种格式，断言文件可被对应库打开、章节数正确
- `test_scope`：工作目录识别与模糊时抛错

组织质量（合并去重、语气）无法单测，通过实际生成若干份报告验收。

## 11. 验收标准

1. 「写今天的日报」能产出 Markdown，数字与 `git log` 一致
2. 禅道不可用时，报告明确写出缺失，且仍能生成
3. 同一周期重复生成结果稳定，不会出现条目数漂移
4. Word 与 PPT 能从 Markdown 渲染，内容与 Markdown 一致
5. 指定受众后语气随之变化
6. 提供模板时按模板章节组织
