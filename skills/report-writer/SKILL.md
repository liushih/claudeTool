# 报告撰写

## 适用场景

- 日报、周报、月报、季度/年度述职
- 把 git 提交与禅道任务整理成汇报材料
- 把已有内容转成 Word 或 PPT

不适用：

- 新业务首次接入 → 先用 `adapter-bootstrap`
- 造数、查库 → 用 `data-gen-core` 或 `db-access`

## 前置检查

1. 读 `<数据目录>/projects/<项目ID>/report.yaml`
2. 项目未指定时，用当前工作目录匹配项目；匹配不到或命中多个就**问用户，不猜**
3. 确认报告类型与时间区间
4. 询问受众（给谁看），再决定语气
5. 述职报告额外询问角色（开发 / 测试 / 产品 / 其他），决定重点与措辞

报告配置缺失时，引导用户补 `report.yaml`，不要现场编造仓库或禅道 ID。

## 路径

命令里的 `<TOOLS_DIR>` 是工具仓库根目录，按顺序确定：环境变量 `DATA_TOOLS_DIR` → `~/.data-tools/config.yaml` 的 `tools_dir` → 问用户仓库在哪，不要猜。通过 `install.ps1` 渲染安装时命令里已是绝对路径，可跳过。

解释器优先用仓库内 `.venv/Scripts/python.exe`；不存在时用 `python`，并先 `pip install -r requirements.txt`。

## 执行

1. **确定项目**：用户明确说了就用它；否则按当前工作目录匹配；不确定就问
2. **确定类型与区间**：日报=当天，周报=本周（周一起），月报=当月，述职按用户给的区间
3. **询问受众**：直属领导（默认）/ 更高层 / 自己留痕 / 团队共享。默认取
   `<数据目录>/reports/<项目ID>/.audience`，确认后写回该文件
4. **询问角色**（述职必问，其它类型可跳过）：开发 / 测试 / 产品 / 其他。默认取
   `<数据目录>/reports/<项目ID>/.role`，确认后写回。用户当次指定优先于记忆值，
   不改配置文件
5. **采集**：

```bash
"<TOOLS_DIR>/.venv/Scripts/python.exe" "<TOOLS_DIR>/scripts/collect.py" \
  --project <项目ID> --type <daily|weekly|monthly|review> [--start <日期> --end <日期>]
```

6. **摆事实**：先报告采集结果（几个提交、几个任务、几个 Bug、哪些源失败），
   再问「有什么没体现在提交和工单里的」。用户补充优先级最高
7. **读模板**：`<数据目录>/templates/<项目ID>/<类型>.md`；没有就用默认结构
8. **撰写**，遵循三条规则：
   - 写结果，不写动作。不要出现「提交了 N 次代码」
   - 合并去重：同一件事既有提交又有任务时合并成一条，以任务标题为主线
   - 数字只作佐证。日报 200–400 字，周报 400–800，月报 800–1500
9. **保存**：`<数据目录>/reports/<项目ID>/<label>.md`（标签由 collect.py 生成，
   如 `2026-10-26-daily`、`2026-W44-weekly`、`2026-Q3-review`）
10. **渲染**（用户要 Word/PPT 时）：

```bash
"<TOOLS_DIR>/.venv/Scripts/python.exe" "<TOOLS_DIR>/scripts/render.py" \
  --input <md 路径> --format docx,pptx --out-dir <同目录> --title <标题>
```

11. **数据缺失**：报告开头显式说明缺了哪个源，例如「禅道数据缺失，本次仅基于代码提交」

默认章节：

| 类型 | 结构 |
|---|---|
| 日报 | 今日完成 / 明日计划 / 风险与需要支持 |
| 周报 | 本周完成 / 关键数据 / 问题与风险 / 下周计划 |
| 月报 | 目标达成 / 关键成果 / 问题与改进 / 下月重点 |
| 述职 | 成果 / 问题与反思 / 规划（有模板则按模板） |

受众与语气：

| 受众 | 语气 |
|---|---|
| 直属领导 | 简洁、结果导向、少形容词 |
| 更高层 | 聚焦业务价值与风险，细节下沉 |
| 自己留痕 | 可以写过程、待办和踩坑 |
| 团队共享 | 强调协作接口与依赖关系 |

角色与重点（述职必用，其它报告可选）：

| 角色 | 重点 | 指标 | 措辞 |
|---|---|---|---|
| 开发 | 交付、质量、技术债 | 提交、修复 Bug、线上问题 | 实现、重构、优化 |
| 测试 | 覆盖、缺陷拦截、质量门禁 | 发现 Bug、用例覆盖、漏测 | 验证、拦截、回归 |
| 产品 | 需求价值、上线节奏、用户指标 | 需求交付数、验收通过率 | 规划、推动、对齐 |
| 其他 | 按用户描述的工作内容归纳 | 以实际数据为准 | 中性 |

角色只影响**怎么写**，不改变采集范围。测试角色的「我发现的 Bug」当前采集不到，
写作时如需这部分素材，向用户索取或明确写「本次未统计发现类缺陷」。

## 失败处理

| 情况 | 动作 |
|---|---|
| 缺 `report.yaml` | 报路径，引导补配置，不现场猜仓库与禅道 ID |
| 项目无法确定 | 停下来问，列出候选 |
| 禅道连不上或未授权 | 只用 git 数据，报告开头写明缺失 |
| 某个仓库不存在 | 跳过该仓库并提示，其余照常 |
| 完全无数据 | 不编造，输出骨架并注明「本周期无提交与任务记录」 |
| 时间区间非法 | 报错，不生成 |
| 渲染缺依赖 | Markdown 照常产出，提示安装 python-docx / python-pptx |
| 受众未确认 | 默认直属领导，并在开头注明所用语气 |
| 角色未确认 | 述职默认开发视角，并在开头注明 |
